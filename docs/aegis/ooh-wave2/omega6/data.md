## ADR 0022 open item: measured on the real ledger (rl_omega6 C_adr_*, both Pythons)
- Set-aside path (C_adr_unappliable_set_aside_late): a tenant_created line without tenant_id is set aside, then its ooh anchor is POSTed. The check appends it and clears discarded, integrity ok:true, audit/integrity ok:true with ledger_valid:true, and the next write is 201 (log 15 = anchors 15). The in-memory state lacks the line (tenants = [acme]). Restart REFUSED: KeyError 'tenant_id'. Read-back and money show no problem. Cause: service.py:396-404. In `_settle_pending`, the set-aside branch keeps `appended` and drops the problem string "an anchored pending line could not be applied; an operator must inspect the log" that `_roll_forward` returns (service.py:438-439).
- For contrast, the file-pending path (service.py:386-388) and the own-pending path (service.py:375-376) report that operator problem: ok:false, write 503. The line is still appended, so a restart is refused the same way (KeyError). In all 3 paths, recovery needs an operator. Only the set-aside path keeps accepting writes on top of the poison line, with no signal.
- Rating: L-4 LOW, NOT BLOCKING. No money is doubled, no data crosses tenants, and nothing is destroyed. The effect is a silent detection gap, and an outage at the next restart that an operator must fix.
- Reachable with this service's own writes: NOT REACHABLE, as far as I measured. A set-aside line is only ever a pending line that _commit wrote, and _roll_forward only accepts it as the exact next line chained to the current log (verify_lines, service.py:411). I inspected all 31 `_a_*` replay handlers (AST scan of src). None reads the clock, settings, or env; each depends only on (d, at) and the state, and the state is the deterministic replay of the same prefix (C1: 692 replay comparisons; the only errors are the 2 deliberately malformed test lines). So on revival, _apply runs as it would have inside _commit (service.py:216). If a line a command built could not be applied, the normal path would already fail, and I saw no such case. To reach it you need write access to the data dir AND the ability to record an ooh log_anchor (service token; department is self-declared, INFO-4). That attacker can already plant a fully appliable forged line that passes integrity, which is worse. So this adds no new capability.
- Reproducer: poc/rl_omega6.py <ledger-bin> <work> <tree>, case C_adr_unappliable_set_aside_late. Falsifier: after the late anchor, integrity is ok:false with the operator problem and the next write is 503 (the same as the file-pending path).
