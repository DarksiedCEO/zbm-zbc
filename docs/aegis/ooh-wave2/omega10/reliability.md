## 4. Failure handling
### 4a. _read_at_start (store.py:134-152), probe_start.py, 3.12 and 3.13 identical (probe-start-*.txt). All cases: leaked fds = [], no hang (each run in a thread with 10 s join).
- os.open raising EIO, ELOOP, ENXIO, EAGAIN, EMFILE, EACCES, EINTR, EROFS, ENFILE, ENOMEM: StoreCorrupt "the log cannot be opened (<class>); refusing to start". ENOENT: starts empty (intended). Fail closed. Note the message tail "it must be a regular file, not a link" is wrong for the transient errnos (EMFILE, ENFILE, EIO, EAGAIN): an operator is told the file type is bad when the process ran out of descriptors. See F4.
- fstat EIO, pread EIO/EAGAIN/EINTR/EINVAL: StoreCorrupt "cannot be read (<class>)". MemoryError and KeyboardInterrupt in pread: propagate unchanged, fd closed (finally). pread returning 7 bytes at a time: starts, 3 lines (the _pread_exact loop works). os.close raising EIO after the real close: start proceeds (quiet close).
- File changing between fstat and read: shrinks to 10 bytes: StoreCorrupt "torn line"; shrinks to exactly one line or to 0: starts with 1 or 0 lines (what is on disk at the read; the next integrity check/write compares file and memory); grows by junk or by a newline after fstat: starts with the 3 lines of the fstat size, the tail is not read. In the grown cases the service's startup integrity check and every write compare file and memory and refuse (see 4c "grows after fstat"); none of these cases corrupts anything.
- Real file states: symlink, symlink to /dev/zero, dangling symlink, unix socket, chmod 000: refuse to start. FIFO with no writer, FIFO held open by another process, directory: "not a regular file", no hang. Empty file: starts empty. Torn tail: refuses.
- Sparse files: 256 MiB and 1 GiB (apparent size): refused ("torn line") but the file is READ whole first: maxrss 279 MiB and 1.30 GiB (rss.py: 1045 MiB at 91ea9a1, 1045 MiB at 0f5fbe3, i.e. the same as the old fh.read()). 3 GiB and 1 TiB: pread fails (EINVAL on macOS) -> StoreCorrupt "cannot be read". No size bound before the read (pre-existing, unchanged; INFO F7).

## Findings
- F1, MEDIUM, class CRASH_UNRECOVERED / PARTIAL_FAILURE_TORN_STATE (fail closed, but wedged across restart). Claim: a single failed close() of the log's READ-WRITE descriptor after a successful pwrite+fsync (store.py:265) lets a raw OSError out of append_prepared. _commit (service.py:210) only catches StoreWriteError, so: the request gets 500 "internal error"; the line is durably in the file but not in memory; self.integrity stays ok (stale); the NEXT write (any other request) prepares the same seq, ANCHORS it in the ledger (service.py:200-207 order: anchor first), and then append_prepared refuses ("log file and memory disagree"), so the ledger holds an anchor for a line that is not the line on disk. Result observed: every later write 503 (STORE_UNAVAILABLE, then INTEGRITY_UNVERIFIED), a retry of the first request id 503, and AFTER A RESTART integrity is false: "the ledger holds anchors beyond the local log: the log was truncated or rolled back"; writes 503 until an operator inspects. No data is lost and nothing is written wrongly (fail closed), but the service does not recover without an operator. Repro: closewr.py (omega10/reliability/closewr-3.13.txt): wrap os.open/os.close so the first close of the O_RDWR log fd raises OSError(EIO) after closing, POST /sources, then POST another /sources, retry the first id, restart the harness. Identical output at 91ea9a1 (pre-existing code; the delta only fixed the read-only close). Likelihood: needs close() to fail on a regular file after a good fsync (NFS or FUSE class; not seen on local APFS or ext4); impact: operator intervention. Falsifier: change store.py:265 to `_close_quietly(fd)` (or catch OSError there) and re-run closewr.py: the first POST should be 201 and the second write should succeed, no wedge. Or show that no filesystem the service is deployed on can fail close() after fsync.
- F2, MEDIUM, class RETRY_AMPLIFICATION / RESOURCE_EXHAUSTION (bounded). Claim: request_sha now runs the full PII screen (NFKC, per-character category loops, 5 regex families, up to 5 redaction passes) on the vendor text of every request body, twice per accepted request, under the service lock and the GIL (service.py:68-84, :273, :285). An idempotent replay of a max-size (4000-char) body went from about 4 ms to 35-56 ms; a fresh request from 54 to 112-139 ms; a flood of replays dropped from 285 to 17 req/s and a cheap GET under the flood rose from 12 to 183-207 ms median (max 338). Bounded by DOC_MAX = 4000 chars and by NFKC expansion (72 000 chars worst, 54 ms), so not unbounded and no timeout is breached (hundreds of ms against seconds). Needs an authenticated caller (or a retrying client with large text). Repro: e2e.py and rsha.py/rsha2.py (e2e-3.13.txt, e2e-3.13-run2.txt, e2e-3.12.txt, rsha-3.13.txt). Not an unbounded-cost or ReDoS defect: the per-character scaling is linear in all 60+ families. Falsifier: show the replay path (service.py:273) skipping the screen when vendor_text is absent or when the raw body hash already matches, or a service-level rate limit that bounds replays below about 20 per second per caller; or measure on a quiet machine a replay under 10 ms.
- F3, LOW, class CLEANUP_SKIPPED (carried predecessor F2/F3, test only): the new FIFO test leaves its FIFO (see section 1) and the write half of the legacy FIFO test has no timeout. Subsumed by F5.

Fail closed is right; the text sends an operator to the wrong cause on a descriptor-exhaustion restart loop. Repro: probe-start-3.13.txt "os.open raises EMFILE". Falsifier: the message names the exception class only.
