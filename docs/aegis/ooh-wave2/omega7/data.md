## Findings
- **M-3 MEDIUM (NEW measurement; the code is unchanged, so it was already present at ce665c5): NO_RESTORE_PATH. At start the service deletes an anchored pending line if the log on disk is one whole line shorter.**
  - Path: service.py:384-403. The file pending line is not chained to the shorter log, so it is "not vouched: stale" and goes to pending.discarded. In the same check, the discarded branch calls clear_discarded() on "stale" without asking whether the ledger holds its anchor.
  - Reproducer: poc/m3_stale_delete.py <ledger> <work> <tree>, case shorten_then_restore (both Pythons the same). (1) An anchored write's append fails (real RLIMIT short write): pending.line on disk, 14 anchors / 13 lines. (2) The process stops, one log line is removed (e.g. an older backup is restored), and the service restarts: "anchors beyond the local log", and pending.line and pending.discarded are both gone. (3) The full log is put back and the service restarts: still "anchors beyond", the line is not applied, writes 503 for good. The ledger holds only payload_sha256, so the line cannot be rebuilt.
  - Controls: control_no_pending (the same truncation with nothing in flight) recovers after the restore (201, 14/14). keep_copy (the operator saved pending.line) recovers (15/15). In rl_omega7 A_shorter_line_at_append_tenant_restart the same thing happens through the at-append path.
  - Impact: fail-closed. No doubled money, no tenant crossing. But a maybe:true write is destroyed, and recovery needs a ledger reconcile that does not exist (INFO-5). Precondition: someone outside the service shortens the log, a pending line exists, and the service restarts.
  - Falsifier: after step 3 the line is revived (applied, anchors == lines), or the stale set-aside is kept while the ledger holds its anchor.
