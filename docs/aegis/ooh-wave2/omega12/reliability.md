## Findings
- R12-1, HIGH, class FAIL_OPEN (also PARTIAL_FAILURE / unbounded-layers). pii.py, decode block of `screen_free_text`: `for _ in range(3): once = html.unescape(decoded) ...` runs at most three passes and then screens only the end state; it is not a fixed point, and when three passes do not reach one there is no fall-back to redact. A card or SSN whose separator is an entity nested four deep is therefore not found and is kept in clear. Repro (depth.py, 3.13): `screen_free_text("4111&amp;amp;amp;nbsp;1111&amp;amp;amp;nbsp;1111&amp;amp;amp;nbsp;1111")` -> kinds [] and the text kept unchanged; the same with "SSN 123&amp;amp;amp;nbsp;45&amp;amp;amp;nbsp;6789" and with `&amp;..#32;`; two nested layers (`&amp;nbsp;`) and three are redacted, four or more are not (amps 3..7 all bypass). End to end (probe_depth_test.py through the service harness h, POST /tenants/acme/campaigns/{cid}/inventory, probe-depth-e2e-3.13.txt): with 2 `amp;` layers 201, personal_data_redacted True, text 'contact [redacted] now'; with 3 and 4 layers 201, personal_data_redacted False, kinds [], the response and the log line hold 'contact 4111&amp;amp;amp;nbsp;1111&amp;amp;amp;nbsp;1111&amp;amp;amp;nbsp;1111 now' (decodes to a card with u+00a0 separators; request_sha is over this text). Fuzz (fuzz3.py, 150 000 inputs, 3.13): 26 kept texts whose fixed-point decode, or an intermediate decode (one or two passes), still holds an e-mail/phone/card/SSN/cluster span, kinds empty. This is the same class as the founder decision for r11 S11-2; the three-pass bound just moves the bypass one layer out, and the new tests (`_unescape`, 3 passes) share the bound so they do not see it. Cost of a fix is small: unescape shrinks the text each effective pass, so a loop to a fixed point is at most n passes of linear work (4000 chars: ms), or redact whole when a fourth pass still changes the text. Falsifier: depth.py amps 3..7 report kinds ['card'] / ['ssn'] (or '[redacted]'), and probe_depth_test.py amps=3,4 report personal_data_redacted True. The security gate owns the PII verdict; here it is a reliability fail-open because the screen's own loop is bounded and the unresolved remainder is kept rather than refused.
- R12-2, MEDIUM, class NON_IDEMPOTENT_RETRY (residual of N1, regression-class unchanged from the predecessor MEDIUM). pii.py:47-48 `_DOM = r"[\w-]+"` and `_WORD_DOM`: \w classifies U+2EBF0-2EE5D as letters on Unicode 15.1 (3.13) and not on 15.0 (3.12), so `screen_free_text("a@b\U0002ebf0d.com")` and its request_sha differ between the two builds (see section 2: 622 code points, 405 of 100 000 paired fuzz inputs when the alphabet includes them). The new comment in pii.py ("the kept text and the request hash depend on the Python build" made no longer true) and the test `test_decisions_unassigned_characters_are_kept_so_the_hash_is_stable` cover only unassigned characters in a neutral context (cp in [0x0378, 0x2FFC, 0x31EF, 0x2EBF0]), where the claim holds. Effect: cross-interpreter replay of such a body returns 409 REQUEST_ID_REUSED (fail closed, no duplicate execution), and the stored text differs. Falsifier: xver3b.py y3.12.json equals y3.13.json (0 differing code points) or the domain classes are pinned to an explicit ASCII/IDNA set.
