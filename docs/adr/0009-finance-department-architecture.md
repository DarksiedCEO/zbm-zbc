# ADR 0009 — Finance (31) Architecture

**Status:** Accepted for build (Sep 26, 2026). **Not certified for any real dollar.** The rails (Stripe Connect,
Trolley), the bank feed and bank transfers, the tax agent, the GL (QBO), the vault (Cybersecurity 22), Clipper
Network, Legal (37), People (43) and push are fail-closed stand-ins; the V&I and Compliance thin clients exist but
are unwired by default. On day one no payee activates, no payable accrues, no invoice issues, reconciliation cannot
match and no payout run proposes anything — by design (spec §G "day-one effect").
**Service:** `services/finance-py`
**Spec:** Finance department (31) locked build spec, rev 1 (Sep 26, 2026) — binding; research report
`reports/Finance department bank grade model.md` (FR) for anything it defers.
**Rules seed:** `services/finance-py/seed/fin_rules_seed.json`, generated by `devtools/gen_rules_seed.py` from the
spec's §B.12 table (FIN-00 … FIN-30, plus FIN-31 added by the media billing amendment below) and §H (FIN-CQ-01 … FIN-CQ-16; FIN-CQ-16 added by the round-17 amendment below), 48 rows,
**SHA-256 `3543dfe2d684047debad8fab19165e28957044281ef5e9da25cee5a8f3b087ce`** (pinned in `src/config.py`; any other
file refuses to start unless `FIN_ALLOW_UNPINNED_SEED=1` with an explicit `FIN_SEED_SHA256`, which marks the service
non-production in `/health`).

## Context

Finance keeps ZBC's and ZBM's books, holds ZBC's client deposits segregated, accrues creator payables from V&I
certifications, runs the weekly payout under maker-checker, nets clawbacks, prepares tax records, reconciles to zero
and closes monthly. It never verifies views (V&I), never sets rate-card policy (Clipper Network), never rules on law
(Compliance 38) and never drafts legal text (Legal 37). Founder-locked facts (§0.1) bind every code path: two entities
that never mix, clipper funds held separate until the job is done, reconciliation to zero, dual control on every
release, no float, only verified views paid, only Andre approves rules and rate cards.

## Decisions

1. **One FastAPI service with verification-py's conventions, copied not imported.** `serve.py` (h11, 16 KiB head
   cap, head/idle deadlines, concurrency limit), `store.py` (hash-chained JSONL, `fin_log.jsonl`), `ledger.py`
   (department `finance`, ids `fin-<abbrev>-<40 hex>`), `founder.py`, `textguard.py`, `rules.py` and the
   `InputLimits`/auth blocks of `api.py` are verification-py's, renamed. Docs routes off; bind `127.0.0.1`
   (`FIN_BIND_ADDR`), port 8410 (`FIN_PORT`); no new dependency (pinned versions of BUILD_CONTRACTS §0).
2. **Identities never interchangeable.** Bearer `FIN_SERVICE_TOKEN` (required to start, ≥ 32 printable ASCII);
   caller `X-FIN-Caller-Token` from `FIN_CALLER_TOKENS` (compliance_38, clipper_network, verification_integrity,
   creative_production, onboarding, legal_37, scheduler, rail_gateway, bank_feed); Andre's `X-Andre-Approval-Token`
   (FounderGate); optional second approver `X-FIN-Second-Approver-Token` (`FIN_SECOND_APPROVER_TOKEN`). All tokens
   distinct or the service refuses to start; a refused approval token is 403 and recorded
   `founder_approval_refused`.
3. **Separation of duties is enforced at the API by caller identity (FIN-19).** V&I reaches only
   `payout-identity`; the scheduler proposes runs, releases approved batches and runs jobs, and can approve nothing;
   Andre approves and cannot release (the release route refuses any request carrying an approval token, 403);
   `rail_gateway`/`bank_feed` push events only; each other department reaches only its protocol routes
   (`tests/test_auth_limits_idempotency.py` checks every caller on every caller route).
4. **Record-first, everywhere, with remote calls outside the service lock.** Every port call is recorded as
   `crossing_<port>_requested` (ids and an argument hash only) and made in a `Gather` phase BEFORE the service lock
   (the AEGIS N16-1 lesson); then the operation's events, then ONE local-log line holding all of its records
   (journal entries included) is anchored on the ledger (`local_log_appended`), appended (fsynced) and applied. Any
   failure → 503 `{"took_effect": false}`. Rail submissions happen outside the service lock inside a per-batch
   non-blocking mutex: intent + F4b/F4c recorded and committed first, then the rail call with the item's idempotency
   key, then the outcome (F4d) recorded.
5. **Event-sourced state and the ADR 0006/0007 anchoring/reconcile regime unchanged** (decisions 4-5, N14-4,
   N15-1, N15-2, N16-7): a disk log that does not match the ledger's anchors refuses to start (fatal: unanchored
   local line, missing cited event, foreign anchors, empty log, mismatched reconcile; voidable: stray anchor, ghost
   effect event, newer lease, a version event matching no local decision). Only Andre's `POST /fin/v1/reconcile`
   voids, with `FIN_RECONCILE_MODE=1`. Effect types for ghost detection: `journal_entry_posted`, `payable_accrued`,
   `batch_approved_by_andre`, `item_submitted`, `rate_card_published`, `callback_recorded`, `invoice_issued`,
   `sweep_approved`, `funding_approved`, `refund_approved`, `top_up_approved`, `clawback_written_off`. The journal
   also carries its own per-entity chain (`prev_entry_sha256`/`entry_sha256`), verified at start (G6).
6. **The journal is the source of truth (FIN-02, FIN-26).** Entries are validated by intelligence 1 before append:
   balanced, ≥ 2 lines, one entity, accounts from that entity's chart with the right sub-ledger kind, canonical
   two-decimal strings, exactly one side per line, no locked period, the restricted-cash rule (FIN-01), 4010/5010
   only from certification flows, manual corrections limited (choice 37). Nothing is ever updated or deleted.
7. **Money is `Decimal`, quantized half-up at creation, a canonical two-decimal JSON string on the wire**
   (BUILD_CONTRACTS §1 with the ADR 0003 §1a bound); a caller's money must be a JSON string (floats, ints, exponents,
   NaN, three decimals → 422, spec A12). Payable = exact `paid_views × rate / 1000`, ONE half-up quantize per
   payable (R1; `2,500 × 0.01 / 1000 = 0.03`).
8. **A payable is created only from what Finance reads itself** (FIN-04): the V&I certification, the Compliance
   payout ruling named by Creative's handoff (subject, gate, time checked), the Andre-approved profile and the
   Andre-published rate card effective at the clip's posting time. Creative's facts are recorded as a hash; any key
   naming a count, metric, amount or rate on a protocol route is 422.
9. **Treasury invariant before every posting (FIN-18).** `1020 + 1040 + 1041 ≥ 2010 + 2020 + 2030 + 2040 + 2050 +
   2070` (stricter than "restricted cash ≥ unearned prepayments"). A posting that would create or deepen a breach is
   refused 409 `TREASURY_BREACH`, except the fact flows (F5a clawback after release, F1a deposit into operating),
   which post, record `treasury_breach`, and turn FC-03 red — runs, releases, sweeps and refunds refused until an
   Andre top-up (F5c) and a green reconciliation.
10. **Maker-checker (FIN-07) and the release gates (FIN-08).** Twelve gates run on every payee at proposal and again
    per item at release, all of them every time; any absent, stale or stand-in input fails its gate; release may only
    narrow a batch. Property-tested over all 2^11 − 1 subsets of absent inputs.
11. **Dual control with one human is a COMPENSATING control, not dual control (R2).** FR: "the person who assembles
    the batch cannot approve it and the approver cannot release it"; a single-person shop's cooling-off period is
    "a compensating control, not dual control"; FR decision 12 "Name a second releaser … before the first batch".
    The founder rule is built exactly (system proposes, Andre approves, system releases), with the compensating
    controls FR names: a 12 h release delay after approval (`FIN_RELEASE_DELAY_H`), a 48 h approval TTL, velocity and
    exposure limits with an Andre-only exception queue, the payee-change callback with a 72 h cooling-off, rail and
    bank controls attested (FC-11, FC-12) and an optional second human approver (`FIN_SECOND_APPROVER_TOKEN` +
    `FIN_DUAL_HUMAN_THRESHOLD`, both tokens in the same decision request). **Andre should know that until a second
    human approver is named this is compensating dual control under the research's definition.**
12. **No custody wording (R5, FIN-29).** The founder's "escrow-style" is honoured as a CONTROL (segregated account +
    the treasury invariant), never as a LABEL: the deposits account is titled `Cash - Restricted: ZBC Client Campaign
    Deposits`; the words `escrow`, `trust`, `FBO`, `for the benefit of` are refused (422 `BANNED_WORD`) in any account
    title, invoice line or template variable, and the chart is checked at import (G8). The custody model is fixed to
    `own_deposit`; any other value refuses to start (FIN-CQ-02).
13. **Clawback is netting only (FIN-16).** No port has a debit, pull or reversal method; a clawback on a released
    payable becomes a receivable netted against future earnings (F4b) or written off by Andre after 180 days (F5b).
14. **Reconciliation to zero (FIN-17).** Legs L1-L4 against the bank, the rail balance/item statuses and the
    operational records; one cent is a break; any open break or a stale run blocks runs, releases, sweeps and
    refunds; only Andre resolves a break.
15. **Rules are data; only Andre changes them (FIN-00).** Proposals `add | amend | retire` with `content_sha256`,
    atomic decisions (≤ 200), 409 on a changed/stale proposal, weakening flagged per changed field and needing
    `acknowledge_weakening: true`; founder rows cannot be weakened; code-cited rows cannot be retired. Rate-card
    versions follow the same pattern (choice 21). Until the seed is approved every action is refused
    `RULES_NOT_IN_FORCE`.
16. **Ports with fail-closed stand-ins; no passing fake in `src/`** (G3). `ports.py` holds protocols and
    `NotWired*`/`NotBuilt*` classes only; the fakes live in `tests/fakes.py`. Production wiring (`api.build_ports`)
    is all stand-ins except the V&I and Compliance thin clients (`src/clients.py`), each wired only when its three
    settings are present (10 s wall-clock budget, one retry, 1 MiB cap, no redirects, compressed answers refused,
    anything inconsistent → the negative answer).
17. **No bank, card, TIN, SSN or DOB data (FIN-28).** Every request body is scanned before the model: keys named
    like such data and values shaped like an SSN/ITIN, EIN, a bare 9-digit routing/TIN number, a Luhn-valid card, a
    mod-97-valid IBAN or a 10-17-digit account/phone run are refused 422 `SENSITIVE_DATA_REFUSED` and never echoed.
    Free-text notes are kept only as SHA-256; the payee record holds the rail's opaque account reference and the
    SHA-256 of the rail's destination fingerprint; the callback contact is a vault reference.

## Choices made where the spec is silent (safest option; for Andre to confirm)

Numbered so code comments can cite them ("ADR 0009 choice N").

1. **Directory name** `services/finance-py` (the brief). **Record shape:** one local-log line per operation
   holding `put` records (collection, id, full record) and `journal` records; state is replayed from them.
2. **Ids** are `fin-<prefix>-` + 26 Crockford base32 derived deterministically from the record's identity (retries
   are idempotent; not time-sortable). Ledger event ids include the caller and `request_id` wherever two callers
   could legitimately cause the same effect.
3. **Concurrency:** one service lock; a second concurrent release of the same batch gets 409 (nothing submitted by
   that call); a sequential second release of a released batch is 409.
4. **F2 and F3 are posted as ONE entry** (memo `F2`, four lines: 2010→4010 revenue, 5010→2020 creator cost), so a
   payable can never have revenue without cost or the reverse.
5. **Fact flows** allowed to breach the invariant: F5a and F1a only (decision 9).
6. **Withholding base:** `withheld = 24% × (gross − netted)`; 1099 reportable = `gross − netted` of PAID items in
   the tax year (America/Los_Angeles release date), box 4 = withheld (CPA question; FIN-CQ-04 area).
7. **Netting-only items:** an item whose gross is fully netted (net 0.00) is a batch item with no rail call
   (status `netted`); it still passes every gate (stricter than necessary).
8. **Minimum:** net below `FIN_MIN_PAYOUT` is carried forward (`BELOW_MINIMUM`, not an error) except a fully netted
   net 0.00; an offboarding payee's minimum is `FIN_FINAL_PAYOUT_MIN` (0.01).
9. **Release only narrows:** an item whose payables changed after approval (a clawback, a revision) or whose
   netting/withholding would differ from the approved amounts is `excluded_at_release` with `CERT_CHANGED`
   (re-propose next run).
10. **Whole-run gates at release** (9, 10, 11 and rules) refuse the release 409 with every item's complete reasons
    and leave items `approved` (retry within the TTL); per-item failures exclude the item for that batch.
11. **One batch per rail per ISO week** (America/Los_Angeles) unless the earlier one was rejected or expired; the
    run weekday and time are the scheduler's to keep (Finance does not refuse a Tuesday run).
12. **Proposal expiry:** a proposed batch not decided within `FIN_APPROVAL_TTL_H` expires (its payables return to
    accrued).
13. **Gate 6 is stricter than a change-only callback:** every payee needs a callback contact on file that the vault
    can confirm (vault stand-in → nobody is payable), and any hold lifts only through an Andre callback to that
    contact plus the cooling-off.
14. **Rail funded before release:** journal 1040/1041 and the rail's own balance must each cover the release total
    (F4a funding is an Andre-approved treasury operation).
15. **Rails in use:** the independent treasury side counts the batch's rail and any rail with journal activity; a
    dormant rail with no activity and a stand-in source is `not_in_use` in L3 (Trolley, R8).
16. **Bank balances are pulled** through the bank port (`balance(entity, account)`); `POST /fin/v1/bank/events`
    carries statement lines (receipts) only.
17. **L4** compares the 2010/2020/2030/1200 control balances with the operational records (payables, items,
    clawback records, receipts, refunds) — a posting and a record that disagree are a break. The "V&I certification
    count ↔ payable count" comparison is not built.
18. **Break resolution** (Andre only): a reconciling entry posted after the break opened; or `timing_in_transit`
    with `clears_by` ≤ 2 business days (status `explained`, blocking again after that date); or evidence once a
    LATER reconciliation run shows the leg matched. Nothing else resolves a break; a difference is never plugged.
19. **Business days** are Monday-Friday; no holiday calendar (B-notice timers, aging, timing items).
20. **Counsel rows** FIN-CQ-01..15 are rule rows of kind `counsel`; one becomes `verified` only through an Andre
    amend whose `parameters.memo_ref` names the memo (weakening-acknowledged). The spec's "via Legal 37 memo intake"
    waits for Legal 37.
21. **Rate-card weakening flags:** creator rate raised, paid-view cap raised, effective earlier than the previous
    version, back-dated `effective_at`; approving one needs `acknowledge_weakening: true`.
22. **Tiering:** a card whose four tier rates are equal is single-rate (T0, no Clipper Network call); a tiered card
    needs the CN tier read (stand-in → `DEPENDENCY_UNAVAILABLE:clipper_network`).
23. **Payee activation body** accepts, beyond `{request_id, payee_id, kind}`, optional `declared_country`,
    `declared_region`, `callback_contact_ref` (a `vault:` reference), `legal_form` and `owner_subject_ids`. Without a
    country no rail can be chosen (refused).
24. **Payout identity** = HMAC-SHA256(vault key, `rail|sha256(destination fingerprint)`) — the raw fingerprint is
    never kept, so the hash of it is the stable input.
25. **Stripe reach** is data (`seed/stripe_reach.json`: US, GB, CA, CH, EU27, IS, LI, NO — not in the research,
    confirm against Stripe's page); Trolley for any other country (dormant).
26. **The sensitive-shape scan refuses look-alikes:** an id containing a bounded 10-17-digit run (or a 9-digit one)
    is refused even if it is not an account number.
27. **Free text** (notes) is stored only as SHA-256; invoice line descriptions and template variables are stored
    raw after the fee-word, banned-word and sensitive-shape scans (they are client-facing text).
28. **Callback contact mismatch** is 422 `CALLBACK_CONTACT_MISMATCH` and recorded as `founder_approval_refused`.
29. **Rail webhooks** are accepted only when the rail adapter verifies the signature (stand-in → every event
    refused 409); duplicates by `(rail, event_id)` are answered `duplicate` with no posting.
30. **A failed or returned item** reverses its F4b/F4c entries (payables return whole to `accrued`, 1200/2040
    restored) besides F4f/F4g, and puts the payee on hold until an Andre callback.
31. **Refunds:** the proposal sets the campaign to `closing` (no new accruals); Andre's approval posts F6; the payment
    posts F6p when the bank adapter accepts it (retried by the `rail-sync` job; stand-in → stays approved).
32. **Top-up (F5c)** is a direct Andre route (`POST /fin/v1/treasury/top-ups`), bank transfer then posting.
33. **Unapplied cash:** a statement line that matches no invoice posts to 2070 and opens a break; Andre may apply one
    that landed in 1020 to an issued deposit invoice of the same total (`POST /fin/v1/receipts/{id}/apply`).
34. **Invoices:** card as a payment method is refused (D11); ZBC invoices are campaign-deposit invoices only; ZBM never
    issues a campaign deposit; recurring mechanics are checked at draft and again at issue.
35. **Disputes:** a card chargeback is refused (card acceptance is off); an invoice dispute (Andre) pauses the
    campaign's accruals and freezes its refunds, and its outcome unpauses it when no other dispute is open; invoice
    disputes post nothing.
36. **Close:** six scheduler tasks (three computed: restricted recon signed = L1/L4 matched, exception aging, 2020/1200
    roll-forward = L4 matched), then Andre's approval locks the period; only a past period can close; statements
    stay `draft` (GL stand-in; FIN-CQ-03/05).
37. **Manual corrections (Andre):** an exact reversal of an existing entry, or lines that avoid restricted cash,
    creator/client liability sub-ledgers, clawback receivables and verified-view revenue/cost.
38. **Jobs** (`accrual`, `clawback-sync`, `tax-sync`, `rail-sync`) are idempotent per (job, UTC date).
39. **Control results:** Andre-owned controls through `POST /fin/v1/controls/{id}/results` with Andre's token; FC-07
    by `compliance_38`; computed controls take no result.
40. **Idempotency:** stored answers are persisted with the operation (they survive a restart); a blocked payout run is
    NOT stored (a retry re-evaluates); a handoff replay re-evaluates (N14-15b) and returns the same payable.
41. **Entity payees** (`legal_form: entity`) need owner subject ids; each owner is screened (role `owner`); none →
    `OFAC_NOT_CLEAR`.
42. **Stricter config floors:** `FIN_OFAC_MAX_AGE_DAYS` accepts only 1; `FIN_ACCESS_REVIEW_DAYS` ≤ 90;
    `FIN_CLAWBACK_WRITEOFF_MIN_DAYS` ≥ 180; `FIN_EVIDENCE_RETENTION_DAYS` ≥ 2557; the release delay must be below the
    approval TTL.
43. **Payees on hold still accrue** (a hold gates payment, not earning).
44. **Rows read per gate:** accrual HR-12/HR-13; tax US-IRS-TIN/US-IRS-BWH (W-9) or US-IRS-FOREIGN/US-IRS-W8-VALID
    (W-8); OFAC US-OFAC-01/02/03; rail US-STRIPE-KYC; recurring US-ROSCA; 1099 US-IRS-1099NEC.

## Spec items not built, and why

- **"Changes other services must make" (below)** — reported, not made (brief).
- **Real adapters** for Stripe Connect, Trolley, the bank feed/transfers, the tax agent, QBO, the vault, Clipper
  Network, Legal, People, push — ports and stand-ins only (spec §G open items).
- **F7/F7a card chargebacks** — card prepayments are off (D11); the route refuses them.
- **F9 Form 945 deposit and F10 rail/processing fees** — no route posts them. Consequence: the first real rail fee
  would open an L3 break that only a correction route for fees can clear (on the unlock list).
- **F1a move of a mis-deposit** as its own flow — handled as a fact flow plus an Andre top-up; applying the 2070
  amount to a campaign from the operating side is not built (only receipts that landed in 1020 can be applied).
- **Intercompany** (a ZBM invoice + a ZBC payable to ZBM from operating cash) — not built.
- **L5 GL tie-out, statements (IS/BS/CF) and the KPI pack** — the GL adapter is a stand-in; the close locks the
  period and reports statements `draft`.
- **The WD1-WD5 calendar itself** — tasks are recorded, not scheduled against workdays; FC-09 is "previous month
  locked".
- **1042-S, the C-13 push to Compliance, IRIS filing** — not built; 1099 preparation records are produced on request.
- **Over-budget decisions** other than a paid top-up deposit (Andre's "operating-funded top-up then accrue" and
  "refuse citing the agreement") — the payable stays `over_budget_hold` until the deposit covers it.
- **Rate-card retire; the CN `view_terms.max_paid_views_per_clip` equality check** — not built.
- **Denied callback → "rail asked to disable the destination"** — no rail method for it; the payee stays on hold.
- **Trolley's batch API** (batch → add payments → start processing) — the rail port models one submission per item.
- **Dispute evidence pack** — built from stored refs only (order form, certification ids, caller refs).

## Known limitations

- Single process, one lock; state rebuilt from the log at start. Ledger writes (record-first) and the FC-04 ledger
  read happen under the lock (the N16-1 class, as in verification-py); every other remote call is outside it.
- Reconciliation and treasury checks read balances with `as_of` ≤ 26 h; the bank and rail are fakes in tests.
- The sensitive-shape scan cannot recognise an account number embedded inside a longer alphanumeric token.
- Jobs run synchronously inside one request.
- The 10,000-payable test runs through service calls (not HTTP) for time; the HTTP paths are covered elsewhere.
- Thin clients were tested only against mock transports; the Compliance sanctions and jurisdiction reads answer
  unavailable because Compliance has no such route for `finance_31` yet.

## Testing

`cd services/finance-py && python3 -m pytest -q` — scenarios S1-S14 (`test_cert_scenarios.py`, including 10,000
random payables), attacks A1-A15 (`test_cert_attacks.py`), the required property over all 2,047 subsets of absent
gate inputs (`test_property_gates.py`), money vectors and a balance-to-zero property (`test_money.py`), guardrails
G1-G9, config refusals and the thin clients (`test_guardrails.py`; G9 is also an autouse fixture that checks every
harness's journal after every test), auth/limits/idempotency and SoD, ledger-failure-has-no-effect,

## Amendment: bug sweep fixes (Oct 6 2026, branch `fix-finance`)

The Oct 6 backend bug sweep (project doc `bug-sweep-2026-10-06`) found that a payout Stripe had accepted could end up
never booked (B-F2, Critical), and that bank receipts and Stripe payments had the same root cause (B-F1, B-F3). It
also found a top-up replay bug (B-F4), an unbooked Stripe Dashboard refund (X-6), tokens in `repr(Settings)` (X-8),
an unbounded lock map (X-10), the old `store.py` fsync bug (F-3/E-5), and the ledger `verify()` running under the
service lock. Each reproducing probe is now a regression test in `tests/test_sweep_fixes.py`; every one fails on
integration 5d49ee9 and passes here.

**Root cause (B-F1..F3).** The journal evidence was recorded under a fixed id, `derived_id("je", entity, key)`, but
its payload carried `entry_sha256`. That hash covers `posted_at` and the chain head, so any retry after a lost anchor
sent a different payload under the same id, and the ledger answered 409 forever.

**Decisions.**
1. **Evidence ids (the bizdev R6 pattern).** Every typed event goes through `Op.record`.
   - The caller's derived id is the action's request key, `rk`.
   - The recorded payload is the caller's payload plus `rk` and `seq` (the log line it is meant for). It never
     carries the wall clock.
   - The recorded id is `i10.evidence_id(rk, type, payload_sha256)`.
   - So the same action, with the same content, for the same line, is the same id and the same payload: the retry
     gets the ledger's 200. Anything else gets a new id, never a lasting 409.
   - Journal evidence binds `content_sha256` over the entity, lines, flow, source, key, reversal and approval. It
     leaves out `posted_at`, the chain head and the effective date. The full entry, `entry_sha256` included, is in
     the anchored log line.
   - Instance leases and reconciles keep their exact ids (`raw=True`), because i10 parses them.
2. **Committed vs attempted.** Each log line names its typed evidence (`data.evidence`: id, type, rk, payload hash).
   - `_commit` refuses (503) if the log moved between an operation's evidence and its commit, so a line is never
     mislabelled.
   - `GET /fin/v1/audit/evidence` marks each Finance ledger event:
     - `committed`: named by an anchored line, payload hash matching;
     - `cited`: a crossing, lease, version or reconcile listed by an anchored line;
     - `attempted`: anything else.
3. **No ghost refusal for a retried action.** `i10.assess` no longer counts a ruling that no line cites as a ghost
   when its id is `evidence_id(rk, type, its payload_sha256)` for an `(rk, type)` that a local line committed. That
   ruling is an earlier attempt at a committed action. Without this, every retried booking would block the next
   start until Andre reconciled. A ghost whose action was never committed is still voidable, as before.
4. **Payout booking (B-F2).**
   - In `_release`, a failure recorded after an item reached the rail is per item: the item answers
     `outcome: unknown_reconciling`, `took_effect: "unknown"`, and the other items go on.
   - `drive_open_items` catches `Unavailable` per item, and so does `retry_transfers` per operation.
   - A 503 raised once money may have moved, in a release or in a bank transfer after the bank call, says
     `took_effect: "unknown"` and `outcome: "unknown_reconciling"`. Only a 503 raised before anything could move
     money says `false`; the API sets `false` only when the error does not say otherwise.
   - A rail `paid` or `failed` event for an item still `submitting` is held (`held_submitting`, recorded as
     `rail_event_held`). It is never acked and dropped.
   - A redelivery of the same event re-applies it instead of answering `duplicate`. Finance also applies it itself:
     right after the item's acceptance is booked, and in every rail-sync job (`replay_held_rail_events`). Each held
     event is applied in its own operation.
   - Treasury operations left `executing` (the bank answered, but the booking could not be recorded) are asked again
     by the rail-sync job with the same key.
5. **Top-up replay (B-F4).**
   - The top-up answer is persisted with the approval commit (`_idem_add`), and so is a treasury decision's.
   - A replay answers the operation's current state.
   - An existing treasury operation is never re-created, so `attempts` is never reset.
   - A posting that was already reversed is never the one a new bank instruction relies on.
6. **Stripe Dashboard refunds (X-6).**
   - `StripePayment.amount_refunded` is the charge's `amount_refunded`.
   - Any increase over what Finance booked posts **F7r**, keyed by the new cumulative total, so it posts once:
     Dr 1100 A/R[client] (2070 if the receipt was unapplied) / Cr 1060.
   - A break `stripe_refund` opens for Andre.
   - A full refund reopens the invoice and withdraws the client receipt (media: `_media_unpaid`).
   - Any refund over 0 on a media prepayment sets `payment_refunded`, which blocks vendor payments (COLLECT_BEFORE_PAY)
     until a new prepayment lands.
7. **X-8.** Every token and key in `Settings` is `repr=False`.
8. **X-10.** The per-batch release mutex is dropped when the batch does not exist or is terminal (settled, failed,
   expired, rejected).
9. **Store (F-3/E-5).** `store.py` is clientfix-py's, without the pending line:
   - exact-size `pwrite` with adopt-if-present and `ftruncate` on failure;
   - `O_NOFOLLOW`;
   - an empty line refuses start;
   - `DataDirLock`: a per-process `flock` taken by `config.load`, claimed once by `api.build_service`, and adopted
     with a single-use token by the service;
   - an inert `close()`: a closed instance refuses every ledger record and commit.
10. **`verify()` outside the lock.** `integrity()` calls the ledger's `GET /ledger/verify` before it takes the
    service lock.

**Live run.** `devtools/live_server.py` gains a one-shot fault (`POST /devtools/ledger/drop-anchor-after-f4d`). The
week-2 release now runs with it armed, so the rail accepts the payout and the anchor of its F4d booking line never
reaches the ledger. Two checks follow:
- the item is booked on the retry within the same release;
- `/fin/v1/audit/evidence` shows that booking committed exactly once, and the lost try as attempted.

The restart leg then verifies every anchor with the attempt still on the ledger. The run is 54/54 checks (was 52).

**Known limitation (not changed).** These fixes cover an anchor that never reached the ledger. A different case
remains: an anchor the ledger DID record, whose answer was lost, followed by a failed local append. That leaves a
stray anchor, which is voidable at the next start and needs Andre's recorded reconcile, as before. bizdev, influencer
and clientfix close this case with the pending-line roll-forward (ADR 0012 H1/N1), which is not ported to Finance yet.
