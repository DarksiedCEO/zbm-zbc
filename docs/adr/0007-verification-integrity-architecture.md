# ADR 0007 — Verification and Integrity (V&I) Architecture

**Status:** Accepted for build (Sep 26, 2026). **Not certified for any real clipper, clip or payout.** The
token vault, every platform adapter, the perceptual hasher, the media intake, the age-assurance provider,
Finance (31), Legal (37), People (43) and Clipper Network are fail-closed stand-ins, so on day one no
connection completes and nothing certifies — by design (spec §G: "nothing is payable on day one").
**Service:** `services/verification-py`
**Spec:** Verification and Integrity locked build spec, rev 1 (Sep 26, 2026) — binding; research notes
`research_notes/Verification and Integrity department/platform_apis_and_fraud.md` for anything it defers.
**Rules seed:** `services/verification-py/seed/vi_rules_seed.json`, generated by
`devtools/gen_rules_seed.py` from the spec's §B.6 table, 28 rows (VI-00 … VI-22 plus VI-15a … VI-15e),
**SHA-256 `875baeda47d647754042b7a5b61d392ae477a89e19310ef56e1eec26372ab309`** (pinned in
`src/config.py`; any other file refuses to start unless `VI_ALLOW_UNPINNED_SEED=1` with an explicit
`VI_SEED_SHA256`, which marks the service non-production).

## Context

V&I is the first-line integrity function the founder asked for on Sep 24 ("a bean counter making sure
clippers play fairly"). It certifies view counts and integrity facts from evidence it fetched itself through
the clipper's own OAuth connection to the platform's official API, and answers Compliance (38), Creative
Production and Onboarding through their existing port contracts. It never pays (Finance 31), never rules on
law or disclosure (Compliance), never judges creative quality (Creative), never recruits or disciplines
(Clipper Network), and never bans anyone on its own. Money never touches it.

## Decisions

1. **One FastAPI service with compliance-py's conventions, copied not imported.** `src/` layout, pydantic v2,
   the same pinned requirements, no new dependency; `serve.py` (h11, 16 KiB head cap, head/idle deadlines,
   concurrency limit), `store.py` (hash-chained JSONL), `ledger.py` (department `verification_integrity`,
   ids `vi-<abbrev>-<40 hex>`), `founder.py`, `textguard.py` and the `InputLimits`/auth blocks of `api.py`
   are compliance-py's, renamed. Docs routes off; bind `127.0.0.1` (`VI_BIND_ADDR`), port 8390 (`VI_PORT`).
2. **Four identities, never interchangeable.** Bearer `VI_SERVICE_TOKEN` (required to start); caller
   `X-VI-Caller-Token` from `VI_CALLER_TOKENS` (compliance_38, creative_production, onboarding,
   clipper_network, finance_31, scheduler; ≥ 32 printable ASCII, all distinct, none equal to the service or
   Andre token); Andre's `X-Andre-Approval-Token` through the FounderGate (a token equal to the service,
   a caller or a reviewer token counts as not configured); reviewer delegates `X-VI-Reviewer-Token`
   (`VI_REVIEWER_TOKENS`) honoured only when People 43 confirms the delegate (stand-in: nobody → Andre only).
   A refused Andre/reviewer token is 403 and recorded `founder_approval_refused`. Auth dependencies resolve
   before the body is parsed, so an unauthenticated caller never learns anything from validation errors.
3. **Record-first, everywhere** (spec §A, §E): each port call is recorded as `crossing_<port>_requested` (ids
   and an argument hash only), then the operation's own events, then the local-log line is anchored
   (`local_log_appended`), appended (fsynced) and applied. Any failure → 503 `{"issued": false}`, nothing
   changed (tested for every write route, `tests/test_ledger_no_effect.py`).
4. **One local-log line per operation.** Where compliance-py writes several lines per ruling, V&I writes one
   line holding every record the operation produced (`{"ops": [[kind, record], …]}`), anchored once — an
   operation is atomic locally, so a crash can never leave half a certification.
5. **Event-sourced state + the ADR 0006 anchoring/reconcile regime unchanged** (decisions 4-5, amendments
   N14-4, N15-1, N15-2): a disk log that does not match the ledger's anchors refuses to start (fatal: rule
   version rollback, unanchored local line — e.g. an injected snapshot line, spec A1 —, missing cited event,
   foreign anchors, empty log; voidable: stray anchor, ghost ruling, newer lease from another instance).
   Only Andre's `POST /vi/v1/reconcile` voids, with `VI_RECONCILE_MODE=1`. Ruling types for ghost detection:
   `certification_issued`, `certification_revised`, `clawback_issued`, `clip_attested`, `result_attested`,
   `hr13_attested`, `age_attested`, `strike_issued`, `ban_propagated`.
6. **Ports with fail-closed stand-ins; no passing fake in `src/`** (G3). `ports.py` holds only protocols and
   `NotWired*`/`NotBuilt*` classes; `tests/fakes.py` holds the fakes. A port that raises is unavailable and
   its exception text is dropped (it can quote a token). Production wiring (`api.build_ports`) is all
   stand-ins except the Compliance thin client (all three `VI_COMPLIANCE_*` set) and the TikTok oEmbed
   client (`VI_OEMBED_ENABLED=1`).
7. **Rules are data; only Andre changes them** (§B.6): proposals `seed | add | amend | retire` with
   `content_sha256`, atomic decisions (≤ 200), 409 on a changed or stale proposal, `approved_by`/`in_force`/
   `rules_version` → 422, every amend flagged `weakening` per changed field, approval of a weakening needs
   `acknowledge_weakening: true`. Until the seed is approved every ruling carries exactly one reason,
   `RULES_NOT_IN_FORCE` (VI-00).
8. **The ten intelligences are pure judgment modules** (`intelligences/i01…i10`); the service owns records
   and ports. Every reason item comes from the closed catalog (`reasons.py`, §A.5), cites exactly one rule,
   carries the rule's first source URL and a ≤ 200-character message with ids, dates and counts only.
9. **Real platform adapters are built but cannot be wired in this build.** `adapters/http_adapters.py`
   (YouTube Data v3 + Analytics, TikTok Display `POST /v2/video/list/`, Instagram media insights, X v2, TikTok
   oEmbed) go through `adapters/base.Http`: a per-adapter (method, URL-prefix) allow-list checked before a
   byte is sent (G7), https only, no redirects, no cookies, 10 s, 5 MB cap, the token only in that request's
   Authorization header, the raw body only hashed. They run only when the vault is wired AND
   `VI_<P>_APP_CREDENTIALS_REF` is set; `config.py` refuses both today.

## Choices made where the spec is silent (safest option; for Andre to confirm)

Numbered so code comments can cite them ("ADR 0007 choice N").

1. **Directory name.** The spec names `services/verification-integrity-py`; the build brief names
   `services/verification-py`. The brief was followed; nothing else depends on the name.
2. **Settlement lag when Compliance is unavailable.** The lead's brief: stand-in default 14 days and mark
   rulings `settlement_source: default`. The spec (§C.2 step 1): unavailable/unverified/out of range →
   negative. Both hold: the default 14 only places the window (so `pending` shows a settle date), the ruling
   always also carries DEPENDENCY_UNAVAILABLE or RULE_NOT_IN_FORCE (VI-21), so nothing certifies on it.
   `settlement_source: compliance_hr13` only when HR-13 is verified with a lag inside
   `[max(7, lo), min(14, hi)]` of its `settlement_lag_days_allowed_range`.
3. **Purgeable platform-data side store.** The evidence log is append-only, so raw platform data the terms
   limit (YouTube channel/video ids, TikTok ids and share URLs, Instagram media ids, X post ids, and the raw
   `post_ref` that names them) never enters it: the log holds SHA-256 (ids) or HMAC (accounts) only, and the
   raw value lives in `VI_DATA_DIR/vi_platform_data.json` (atomic rewrite, 0600), purged by the retention
   job (§B.5). The side store is not anchored, so every fetch first checks its raw values against the log's
   hashes (a tampered value is never used: `platform_data_mismatch`).
4. **(see decision 4)** one line per operation.
5. **Ids** are ULID-shaped (`vi-<prefix>-` + 26 Crockford base32) but derived deterministically from the
   record's identity (so retries are idempotent); they are not time-sortable.
6. **The vault builds the OAuth authorization URL** (`TokenVault.authorization_url`): authorization
   endpoints and client ids are not in the research and belong with the client secret in Cybersecurity 22's
   vault. The PKCE verifier and the OAuth `state` live in memory only (10-minute TTL; only the state's SHA-256
   is recorded); a restart invalidates pending starts.
7. **The identity HMAC key comes from the vault** (`identity_hmac_key()`), not an environment variable
   ("from vault", §B.1). Stand-in → identity checks `incomplete`, connections refused.
8. **Exact scopes.** A grant whose scopes differ in any way from §C.1's list is refused (NOT_CONNECTED) and
   the grant destroyed. X scopes (`tweet.read`, `users.read`) are not in the research (UNVERIFIED; X is off).
9. **Adapter fields beyond the research are UNVERIFIED** and must be checked before wiring: YouTube
   `channels.list mine=true`, `snippet.channelId/publishedAt/description`; TikTok `user/info` `open_id`;
   Instagram host/version `graph.instagram.com/v22.0`, `/me` fields, media `timestamp/owner/caption`, lookups
   by numeric media id only; X `users/me` and tweet fields; the TikTok cover-image GET (only with
   `VI_TT_COVER_PDQ=1`).
10. **Liveness days.** Required days are every UTC date after the posting date through the date of
    `min_live_end`; the settlement fetch (at `settle_at ≥ min_live_end`) is the closing check. Today's
    missing check is not a gap until the day has passed. A TikTok oEmbed `gone` is never a deletion signal
    (only a positive fallback), and oEmbed runs only with `VI_OEMBED_ENABLED=1` (explicit network egress).
11. **Certification lifecycle.** The `certify` job (idempotent per UTC date) re-evaluates every `pending` and
    `not_certified` record daily; a blocker that is later cleared (a hold released, an age check done, rules
    approved) lets the record certify with the settlement snapshot already fixed. `certified_views` is the
    first payable-metric snapshot fetched in `[settle_at, settle_at + VI_SETTLE_FETCH_GRACE_H]`; without one
    the record stays `pending` until the grace ends, then `not_certified` (SETTLEMENT_SNAPSHOT_MISSING).
12. **Revision watch end** = `max(create_time + VI_REVISION_WATCH_DAYS, settle_at)`, so a minimum live period
    longer than the watch still gets watched after settlement.
13. **Quota priority.** Settlement and approval fetches may use the YouTube reserve; everything else is capped
    at `VI_YT_DAILY_UNITS − VI_YT_RESERVE_UNITS`. The scheduler order is liveness → metrics → revisions →
    anomaly → certify → retention; liveness serves clips inside their min-live period first. X spends against
    `VI_X_MONTHLY_RESOURCE_BUDGET` (0 = nothing).
14. **Auto-upheld findings** (objective platform evidence): deleted before min live, caption changed, hash
    mismatch (`integrity_fail`) and platform stripped. Their strikes issue at once. Bought engagement,
    stolen content, duplicate identity and account sharing are decided by a human.
15. **Platform stripping** is measured cumulatively against the originally certified count; one finding per
    certification.
16. **Anomaly screen timing and baseline.** Pending clips are screened daily once two views snapshots about
    24 h apart exist, and once more at settlement; an anomaly hold (keyed by its reason codes) is not reopened
    after a human decides it. Velocity = the clip's peak 24-h gain vs the median peak of the clipper's certified
    clips on the same platform (last 20; YouTube never mixes the two sides of Aug 24, 2026), with
    `VI_ANOM_MIN_HISTORY` (5). Instagram watch time only when a duration is known (the adapter returns none →
    `not_applicable`). Cap proximity reads a `view_cap` port on Clipper Network (no protocol exists; stand-in →
    unavailable → INSUFFICIENT_SIGNAL). Geography needs the campaign's targets, so submissions take an optional
    `target_regions` (ISO2) — named so because `target_countries` contains "count", which callers may not send.
17. **Stolen-content check.** No `media_ref` → incomplete → hold for a human; the media intake alone is not
    required when the hasher is wired (the perceptual comparison is complete); matches are exact SHA-256 or
    `PerceptualHasher.match` (the provider's own threshold). Another submission with no readable file at all
    is skipped in the comparison (its own check is incomplete and held for a human); one whose signature is
    missing makes this check incomplete (a re-encoded copy of it would go unseen).
18. **Duplicate identity ordering.** The first clipper to hold an HMAC is the older identity; the hold goes on
    the newer. Ownership outlives a revocation, so a later connection of the same account by another clipper
    is ACCOUNT_SHARED for a human to decide.
19. **Bans** need the clipper_network caller token AND Andre's token (spec A11 lists the ban route with the
    approval routes). A ban is accepted without a V&I recommendation (the restrictive direction) and records
    `recommended_by_vi`. It revokes the clipper's connections and blocks every account, email and payout HMAC
    V&I holds for that clipper. There is no unban route.
20. **Overturn** marks the finding overturned, its strikes `overturned` (`strike_lapsed`) and its holds
    released; a voided certification is NOT restored (Finance and Andre decide).
21. **Strike expiry** (S1 90 d, S2 180 d) is evaluated at read time; no event is recorded for it.
22. **Age method values.** `self_declaration` and `debit_card` are accepted as values only to be refused
    (AGE_METHOD_NOT_HIGHLY_EFFECTIVE, no provider call). A non-neutral DOB field → `inconclusive`. A subject
    with a `minor` attestation stays `minor` (no re-attempt under another DOB). The DOB goes to the provider in
    memory only. A provider DOB disagreement opens a human hold (`age_review`). A minor's data is purged at
    once (well within `VI_MINOR_PURGE_HOURS`), connections revoked.
23. **Port answers are recorded** before they are answered: `hr13_attested`, `clip_attested`, `result_attested`
    and `age_answer_issued` (the spec's §E list has no event for them). Attestations replay like compliance-py's
    gate rulings (N14-15b): same `request_id` + body → the stored answer only if the outcome is unchanged.
24. **HR-13 answer fields.** `verified_views` reflects the certification and the request's facts only (§D.1);
    `still_live_at_minimum_period`, `anomaly_screen_passed` (screened, no anomaly hold open, and either the
    screen found nothing or every anomaly hold on the clip was released by a human), `purchased_engagement`
    (true when no screen exists)
    and `copyright_strike` carry their own reasons in the same list. `copyright_strike` stays true until Andre
    verifies VI-22 (seeded `unverified`) and Legal 37's takedown intake answers.
25. **`attest_result`:** `source: self_reported` → FACTS_MISMATCH (VI-20); the platform is compared
    case-insensitively with the registration.
26. **Seed statuses.** VI-15c/d/e (retention terms UNVERIFIED) and VI-22 are seeded `unverified`; an
    unverified rule never supports a positive ruling. Founder rules (VI-00, VI-06, VI-11, VI-21) can be amended
    only without any weakening reason. Rules the code cites (the catalog, VI-02, VI-15a-e, VI-16) cannot be
    retired. Floats are refused in rule parameters (thresholds are config).
27. **VI-21 scope.** A positive certification relies on VI-01, 03, 04, 06-14, 17-21 and every Compliance row
    they cite (HR-13, CQ-11, US-FTC-465-08, HR-02, AGE-01, HR-03); an `adult` age answer on VI-11 and VI-21
    (HR-02, AGE-01, HR-03). Per the spec's table VI-06 (and VI-05) cite CQ-11, a counsel question that is
    unverified in the Compliance seed — so **nothing certifies until a counsel memo resolves CQ-11**.
28. **Forbidden caller keys** are searched at every nesting level (`views`, `count`, `metric`, `amount`,
    `rate`, and any key starting `guardian`); the one exception is `facts.reported_views` on
    `/vi/v1/results/attest`.
29. **Request limits:** submissions 32 KiB, results/attest and rules 64 KiB, reconcile 1 MiB, else 16 KiB.
30. **Config that asks for something not built refuses to start:** `VI_VAULT`, `VI_HASHER`, `VI_AGE_PROVIDER`,
    `VI_MEDIA_INTAKE` other than unset/`none`; any `VI_<P>_APP_CREDENTIALS_REF`; `VI_DEVICE_SIGNALS_ENABLED=1`;
    `VI_YT_IDS_PER_CALL` ≠ 1; `VI_COUNT_SOURCE` ≠ `owner_oauth_api`; Snapchat/Twitch/X in
    `VI_PLATFORMS_ENABLED`; a partial `VI_COMPLIANCE_*` set.
31. **Extra read routes:** `GET /vi/v1/integrity` (the C-11 analogue: log chain, anchors, leases, ghosts and
    snapshot payload hashes vs the ledger) and `GET /vi/v1/intelligences`.
32. **Jobs** are idempotent per (job, UTC date) through a `job_run` record written at the end; a job that
    failed midway has no `job_run` and can run again that date (its per-clip steps are idempotent).
33. **Connection refresh.** When a connection's raw account id reaches 30 days, the retention job re-reads the
    account (a new fetch); same HMAC → refreshed, otherwise purged.
34. **A1 snapshot evidence.** Each snapshot's ledger event payload is the snapshot record; the certify job reads
    `GET /ledger/entries` once per run and refuses a settlement snapshot whose payload hash differs
    (SETTLEMENT_SNAPSHOT_MISSING), and `/vi/v1/integrity` turns red.
35. **The Compliance thin client** caches rows ≤ 1 h and drops the cache when a newer `register_version` is
    seen; Compliance's register-row answer carries no `seed_pinned`, so it is not checked.

## Amendments — AEGIS round 16 (fix wave 17, Sep 26, 2026)

- **N16-1 — no Compliance call under the service lock; a true wall-clock budget.** The thin client
  (`compliance_client.py`) now runs each exchange in a daemon thread and waits at most the remaining 10 s TOTAL
  budget (both attempts), so a server dripping one byte every few seconds cannot stretch a call (the old code
  checked the deadline only after a chunk arrived: 19.6 s against a 9.8 s drip); encoded answers are refused. The
  service never calls Compliance while holding its lock: `_compliance_snapshot` reads every row a ruling needs
  BEFORE the lock (the `certify` job once per run — HR-13 plus every basis row of the rules it relies on — the
  HR-13 attestation when no window exists yet, and each age read), recording each crossing on the ledger first and
  fetching the rows in parallel within one bounded budget; inside the lock `_compliance_row` only reads that
  snapshot (a row it lacks is unavailable) and re-judges a cached `verified` row against its `expires_at`
  (`RegisterRow` now carries `verified_at`/`expires_at`). Proof: `tests/test_aegis16.py` (drip, lock, once-per-run,
  expiry) and the live drip probe (an unrelated GET answers in < 1 s while Compliance drips).
- **N16-3 — age attestations per caller namespace.** `POST /vi/v1/age/checks` files under (caller, subject id);
  `GET /vi/v1/age/subjects/{id}` reads the caller's own namespace; V&I's own rulings about a clipper
  (certification, integrity, retention, identity) read Clipper Network's. The minor lock holds per (namespace,
  subject) and, for Clipper Network subjects, follows the identity: a subject whose e-mail or payout-identity HMAC
  belongs to a clipper with a `minor` attestation is `minor` too (at the age check and at every read). Only a
  Clipper Network minor revokes connections and purges platform data (the only subjects V&I holds data for).
  Attestations recorded before namespacing carry none and are read by no caller (fail closed: a re-check).
  **Every other route keyed by a caller-supplied subject id — cross-caller design note:** `connections/start`,
  `/complete`, `/revoke`, `identity/checks` and `bans` have ONE writer (clipper_network), so the id space is Clipper
  Network's; `GET /connections`, `GET /clippers/{id}/integrity`, `GET /certifications?clipper_id=` and
  `GET /findings/{id}` are reads of that same space by the departments the spec names (compliance_38,
  finance_31); `POST /submissions`, `/approval`, `clips/attest` and `results/attest` have ONE writer
  (creative_production) and `clips/hr13` is Compliance reading Creative's submission by design (spec D.1: the
  facts must equal the registration, else FACTS_MISMATCH); `GET /age/attestations/{id}` takes a V&I-issued id.
  Only the age routes had two writers; they are the ones namespaced.
- **N16-6 — wire contract with Clipper Network.** Every POST answer echoes `request_id`; every answer another
  department's thin client reads carries `rules_pinned`. `/age/checks` answers `status` (adult / minor /
  unknown) and a `facts_sha256` over what was sent WITHOUT the DOB (a DOB's hash is guessable, so it is never
  echoed); `/age/subjects/{id}` adds `status` and `attestation_id`. `GET /connections` answers
  `{clipper_id, items, rules_pinned}` (was a bare list); the strike feed adds each strike's findings'
  `evidence_ids` and clip `subject_refs`; identity findings carry the id of the check or connection that found
  them as evidence. New reads: `GET /vi/v1/findings/{id}` (clipper_network, compliance_38) and
  `GET /vi/v1/certifications?clipper_id=` (clipper_network, compliance_38, finance_31; with
  `revision_watch_end`). clipper-network-py `tests/test_contract_vi.py` runs CN's real client against this app.
- **N16-7 — a version event alone never bricks start-up** (identical in compliance-py and clipper-network-py). A
  `rules_version_published` event is honoured only when its id and payload hash match a decision record in the
  local log; any other one in this log's epoch is VOIDABLE (not fatal): normal start refuses, reconcile mode
  starts, and only Andre's recorded reconcile voids it (README "Reconciling …"). An empty log no longer treats a
  version event alone as proof of a deleted log (every real version follows its decision line's anchor). This
  replaces ADR 0006 N15-1's "no reconcile can void a published version": a genuine rollback now also reaches
  Andre as a voidable item — voiding it is his deliberate, recorded rules rollback; restoring the unwritten line
  keeps the version.
- **N16-8 — latent certification and age gaps closed.** A fetch answer whose `source_endpoint` is not one of the
  platform's documented endpoints (`platforms.FETCH_ENDPOINTS`; the test-only `fake` name is gone from
  `src/`) or that carries no 64-hex `source_response_sha256` is not evidence (no snapshot, no liveness, never a
  certification). Age: only an explicit `dob_consistent: true` passes; a provider result checked more than
  `VI_AGE_ATTESTATION_VALIDITY_DAYS` (365) ago, in the future or unreadable is `inconclusive`; an adult
  attestation is valid that long from the provider's check time and then reads `unknown` ("expired … a re-check
  is required") everywhere (spec C.5 said "No expiry for adult": amended by the lead's instruction).
- **N16-12 — e-mail normalisation** is NFKC + case-fold + trailing dots of the domain removed. Plus-tags and dots
  in the local part are kept as-is (spec C.7 choice: they are different mailboxes at many providers; the payout
  identity catches the same person).

## Spec items not built, and why

- **"Changes other services must make" (1-7)** — reported, not made (brief: do not modify other services).
  Until creative-py/compliance-py/onboarding-py add their V&I thin clients, they keep their "not allowed yet"
  stand-ins and V&I receives no submissions from Creative.
- **Real vault, hasher, age provider, media intake**, and the Finance/Legal/People/Clipper Network ports —
  stand-ins only (open items §G).
- **PDQ of the TikTok cover vs frames of the submitted file** — needs the media intake and a frame API on the
  hasher; the build compares approval-time and settlement-time cover PDQs instead (both from TikTok).
- **Device fingerprint / IP /24 signals** — not built; enabling them refuses to start (VI-CQ-04).
- **Evidence deletion after `VI_EVIDENCE_RETENTION_DAYS`** (2557 d) — statistics live in the append-only log;
  deleting them needs a log-compaction procedure anchored on the ledger. Nothing is due before 2033.
- **YouTube video × day × country**, `non_public_metrics` on X, Instagram oEmbed — not used (UNVERIFIED or
  excluded by the spec).
- **A push feed to Finance** — pull routes only (`/vi/v1/clawbacks`, certifications).
- **Creative's rulebook GET / kit read** — not called; submissions carry `min_days_live` and seed refs.

## Known limitations

- Single process, one lock around every operation; state is rebuilt from the log at start. The certify job
  reads the whole ledger once per run (ledger-rust has no filtered read).
- Remote calls still made under that lock (the N16-1 class, not reachable in production today): the ledger itself
  (record-first needs its order), and the vault, platform adapters, TikTok oEmbed, hasher, media intake, age
  provider, Finance, Legal, People and Clipper Network ports — all fail-closed in-process stand-ins in this build
  (oEmbed is only reached with a `share_url`, which only a wired adapter supplies). Wiring any of them must first
  move its call out of the lock the way the Compliance reads were (prefetch, or an I/O phase before the lock).
- Ledger volume: every operation records its crossings plus one anchor; the 32-day live run with 9 clips
  wrote ~6.8k events.
- Pending OAuth starts, TikTok/Instagram per-minute/second quota windows and 429 back-off live in memory.
- A copy of the data directory started while the original is idle is detected only once one of them writes
  (leases are checked at start and by `/vi/v1/integrity`) — same as compliance-py.
- Anomaly thresholds are internal-policy placeholders ("no primary source publishes numeric thresholds").
- The real adapters were tested only against mock transports; the platforms' real behaviour, app review and
  quotas are unverified.
- Jobs run synchronously inside one request; large volumes would need batching.
